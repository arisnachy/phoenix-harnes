# Agent Note: Cordis 可视工作区

Status: implemented

[English](2026-09-13-cordis-visual-workspace.md) | 中文

## 问题

Phoenix 已经能够在对话旁边以 in-flow 方式显示 KIRA／子智能体卡片，但由 Cordis 驱动的可视内容此前没有协调一致的呈现区域。显示图片、视频、网页、辅助文本、应用、游戏、仪表盘、编辑器或其他交互式界面时，要么会替换对话上下文，要么打开无关的浏览器界面，要么可能覆盖聊天。当 KIRA／子智能体卡片和 Cordis 内容同时活动时，这个缺口尤其明显：两者需要可预测的右侧区域，Cordis 必须能够出现在 KIRA 下方，而 Cordis 关闭后还必须精确恢复用户之前的外壳状态。

## 决策

布局服务为 `subagent` 和 `cordis` 暴露命名的可视工作区占用状态，但两者承担的几何职责有意不同。展开的 KIRA／子智能体卡片本身已经在 center flow 中预留宽度，因此 `subagent` 占用只是用于协调垂直堆叠的元数据；它不会收起导航，也不会接管普通详情列。

Cordis 才负责临时外壳转换。`ui-workspace` 提供 `ctx.visualWorkspace`；第一次调用 `show()` 时会保存当前侧边栏和详情栏偏好，将 `cordis` 标记为活动占用者，把导航最小化为 Phoenix 的紧凑 56px 控制栏，并关闭普通详情列。Cordis 自身通过 `shell.overlay` 渲染成位于对话旁边、宽度受约束的 in-flow 可视轨道，因此聊天区域会向左让出空间，而不是被覆盖。用新的 Cordis 内容替换当前内容时会保持同一个活动租约，因此外壳不会来回跳动。

当只有 Cordis 活动时，它使用完整的可视轨道。当展开的 KIRA／子智能体卡片也处于活动状态时，同一个 overlay 轨道会变成垂直堆叠：KIRA 保持在上方，Cordis 使用剩余的下方区域。在窄屏幕上，该轨道会移动到对话下方，而不是横向挤压聊天。关闭 Cordis 时只释放 `cordis` 占用，并精确恢复 Cordis 打开时保存的侧边栏和详情栏快照；仍然活动的子智能体占用状态会被保留。

Cordis 被明确设计为**通用界面宿主**，而不是封闭的媒体查看器。它的主要接口接受带有 `render(): ReactNode` 的 `CordisVisualSurface`，因此任何 Phoenix 客户端插件都可以在其中挂载应用、游戏、编辑器、仪表盘、地图、终端、模拟器、表单、生成式 UI 或未来新增的任何可视能力，而无需修改 Cordis 本身。`image`、`video`、`page` 和 `text` 仅作为向后兼容的便捷描述符保留。HTTP(S) 页面仍然在沙箱化 iframe 中呈现，并提供显式的外部浏览器打开入口；视频继续使用原生控制。公共控制器仍然只负责呈现：Cordis 本身不会授予新的执行权限；任意自定义界面只能使用挂载它的插件原本已经拥有的权限和 harness 连接。

轻量级的子智能体 header／catalog 弹窗不算可视工作区占用者。只有真正展开的 KIRA／子智能体卡片才报告 `subagent` 占用，从而避免普通菜单错误地让 Cordis 进入半高布局。

## 曾考虑的替代方案

**为 Cordis 创建独立且无关的模态窗口。** 这样无需协调外壳，但会覆盖对话，也无法与 KIRA／子智能体内容组合，并且会在 Phoenix 内部引入第二套窗口管理模型。

**直接复用普通工具详情面板。** 详情 slot 按会话作用域工作，并与所选工具调用语义绑定。Cordis 必须能够在没有所选工具调用时展示内容，因此接管该 slot 会把两个不同的生命周期混在一起。

**为每个可视占用者预留第二个固定外壳列。** 这是最初的实现方向，但会因为 KIRA 卡片本身已经占用 center-flow 宽度而重复压缩对话。最终设计让 KIRA 保持 in-flow，仅在 Cordis 活动时关闭普通详情列，并使用一个共享 overlay 轨道。

**一个界面打开时关闭另一个。** 这种做法简化几何布局，但会丢失有用的并发上下文。明确要求是 Cordis 可以在已经打开的 KIRA／子智能体界面下方出现，因此拒绝互斥方案。

**Cordis 关闭后恢复固定默认布局。** 这会破坏用户调整过的面板状态。因此 Cordis 会精确恢复打开前的侧边栏和详情栏偏好。

**枚举 Cordis 能显示的每一种内容。** 如果持续扩展 image／video／page／text／app／game／chart 这样的联合类型，每增加一种能力都必须发布新的 Cordis 版本。通用 render surface 让工作区保持开放，同时仍为常见内容保留内置适配器。

## 测试

`ui-layout` 测试覆盖独立的子智能体占用、Cordis 快照与恢复、Cordis 活动期间对导航和详情行为的保护、占用订阅、重复写入以及不持久化。AppFrame 测试验证 Cordis 会最小化导航且普通详情保持关闭，同时验证仅有子智能体占用时不会重复压缩外壳。`ui-workspace` 测试覆盖 Cordis 激活、原地替换内容、关闭／dispose 释放、任意交互式 React 界面、图片／视频／网页／文本兼容性、沙箱化 HTTP(S) 页面、非法 URL 拒绝，以及在活动子智能体界面下方堆叠。KIRA 插件测试验证真正展开的卡片能够获得用于报告占用状态的 layout 接口。

## 后果

Phoenix 获得一个协调一致且开放扩展的可视工作区，而不是多个临时拼接的覆盖层或固定媒体查看器。Cordis 可以在保持对话可见的同时承载 Phoenix 插件能够渲染的任何界面；常见网页、图片、视频和文本无需迁移即可继续工作。展开的 KIRA／子智能体卡片可以与它共存并位于上方；Cordis 会临时最小化导航但不会抢占普通详情生命周期；关闭 Cordis 后会精确恢复用户之前的外壳几何。桌面端可视轨道刻意保持受约束，而不是变成自由调整大小的第四个外壳列。未来的多窗格工作区可以增加独立调整大小能力，而无需改变命名占用者或通用界面契约。
