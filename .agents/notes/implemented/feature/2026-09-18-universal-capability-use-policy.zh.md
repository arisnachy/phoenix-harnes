# Agent Note: 通用能力使用策略

Status: implemented

[English](2026-09-18-universal-capability-use-policy.md) | 中文

## 问题

PHOENIX 已经拥有很广的能力面：持久记忆、会话检索、文件、Web 访问、Code Mode、可视化渲染、连接器、调度、后台任务、子代理以及 HARDNESS 能力索引。剩余的主要失败模式不是“没有工具”，而是编排质量不一致。不同模型供应商可能在存在更权威数据源时仍选择通用途径，用模型记忆回答需要最新信息的问题，根据不完整预览推断文件内容，遗漏相关历史上下文，用文字替代用户明确要求的视觉产物，或者在检查原生能力之前就去发现连接器。这些行为会让已经具备能力的系统表现得像缺少能力，同时增加延迟、token 消耗和不必要的授权流程。

## 决策

所有面向模型的完整 HARDNESS scope 都安装稳定的 `hardness:capability-operating-protocol` 区块。该策略在使用工具前给每个模型相同的紧凑决策顺序：先确定权威数据源，再恢复真正相关的上下文，优先选择最具体且健康的原生能力；当时效性重要时使用实时公共证据；只有在任务需要账户私有状态时才使用已连接的私有来源；涉及文件内容的判断必须先读取真实文件；当用户要求视觉交付物时应使用可视化或生成式能力，而不是用文字假装完成。

该策略仍然受真实能力约束。它不会授予权限、虚构不存在的工具或绕过审批。本次审计确认了几个真实的原生缺口：GUI computer-use/浏览器控制、生成式图片创建/编辑，以及通用事件源/条件监控执行。当官方 registry 中经过治理的连接器能够提供缺失的专用或外部能力时，Phoenix 会进入现有的连接器清单、发现和安装协议。只有在真正挂载 acquisition provider 时，HARDNESS acquisition/building 才被视为可用；当前生产 adapter 创建 acquisition registry 时没有 builders，因此不能把它描述成凭空制造能力的万能后备。未来或重复工作使用持久任务系统，而不是让 Agent 空转。条件监控在存在事件驱动连接器时优先使用事件；否则使用有界的定时检查。工具失败必须先分类，再恢复，避免把授权失败、临时网络失败、能力缺失、输入无效和证据过时都当成同一种错误反复重试。

该协议还规定延迟与成本底线：已经知道健康能力时不重复枚举库存；安全时可以批量执行彼此独立的只读工作；子代理只用于真正独立的工作、验证或审查，并遵守共享预算。面向用户的输出展示结果与证据，不暴露内部路由机制或私有推理。

## 验证

`packages/hardness/adapters/tests/capability-protocol.spec.ts` 固定验证注册顺序，以及数据源权威、时效性、文件检索、视觉交付、自动化、有界恢复和低开销规则。`packages/hardness/adapters/src/index.ts` 会在面向模型的 scope 中把该区块与现有 HARDNESS、主动性、人性化存在感和连接器协议一起安装。

## 备选方案

**依赖每个模型供应商自己推断正确的工具策略。** 未采用，因为模型供应商切换后，产品行为会变化，即使 PHOENIX 实际拥有相同的工具与状态。

**把每个工具 schema 和所有特殊情况塞进一个巨大 prompt。** 未采用，因为这会增加 prompt 成本、降低缓存稳定性，并重复已有 registry 对可执行能力的描述。

**为所有用户请求硬编码一个确定性 router。** 未采用，因为意图分类和工具选择仍有语义部分，而 HARDNESS 已经负责确定性的工作流选择和能力验证。新策略只指导模型，不创建第二个执行 authority。

**把这些规则并入连接器协议。** 未采用，因为连接器选择只是整个决策的一条分支。即使不存在连接器，本地文件、会话记忆、公共 Web 证据、可视化渲染、原生工具和定时工作也应遵守相同的“来源优先”策略。

## 影响

面向模型的 scope 会增加一个很小且稳定的 prompt 区块，换来跨供应商更一致的能力使用。该变化应减少不必要的连接器发现、过时答案、猜测文件内容、重复工具调用，以及对视觉请求使用文字替代。实际执行仍取决于已挂载能力和现有审批、隐私、安全与验证边界；策略本身不会把不存在的 provider 变成真实能力。该变更给 Phoenix 增加的是对这些缺失能力家族的正确识别、路由、发现和治理，而不是伪装成已经内置的电脑控制或图片模型。
