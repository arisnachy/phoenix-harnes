# Agent Note: Pearl Light 风格的模型提供方分步设置

Status: implemented

[English](2026-11-21-guided-model-provider-settings.md) | 中文

## Problem

设置 → 模型原先把所有提供方显示为冗长的技术行，并重复放置编辑、排序和删除操作。API 密钥、账号授权和高级模型目录同时出现，即使某些提供方实际上只支持一种连接方式。这个页面与 Phoenix 的整体视觉语言不一致，也让普通的提供方修改变得像手动编辑配置文件。

## Decision

`ModelsSection` 把已配置的提供方显示为可搜索、响应式的卡片目录，颜色全部使用主题变量。单独的排序操作继续使用已持久化的 `user-profile.modelProviderOrder`。同一编辑器服务于已配置和待添加的内置提供方，依次显示可用连接方式、配置及检查三个步骤；`CustomProviderCard` 依次显示标识、配置及检查。编辑现有提供方不需要重新创建。

连接方式来自 Host 实际注册的授权流程。OpenAI Codex 保持账号登录，ChatGPT Web 保持浏览器会话；没有授权流程的 API 提供方不会显示虚构的 OAuth 选项。API 密钥仍通过 `credentials.set` 只写保存，不进入设置值。成功的账号连接可移除用户层的 `apiKeyEnv` 覆盖，但不删除其他配置仍可能使用的凭据。最终页面明确区分模型发现与端到端请求：发现失败不会清除有效草稿。

`ProviderEditor` 和 `CustomProviderCard` 在没有 `guided` 参数时继续支持原来的直接编辑界面。模型设置页面启用引导，而首次使用流程和专用消费者不受影响。所有界面颜色使用现有的 `--dsw-alias-*` 变量。

## Alternatives considered

**替换设置与凭据服务。** 拒绝：现有服务已保护密钥值、支持版本冲突防护和模型发现。

**必须成功发现模型才可保存。** 拒绝：部分适配器没有可读取的目录，即使发现失败也可能正常执行推理请求。

**强制所有提供方使用同一种认证方式。** 拒绝：API 密钥、账号登录和本地提供方的能力并不相同。

## Consequences

用户先选择提供方，再完成凭据和高级设置；编辑现有提供方也遵循相同流程。凭据值不会进入设置快照。最终检查提供无损连接探测，但保存不等于确认推理可用。针对该页面的回归测试验证分步导航不会提前写入配置。

## 后续：真实 OAuth 和本地 Ollama 管理

模型设置使用遵循主题的响应式分步弹窗，不再内嵌编辑卡片。认证选择基于 Host 实际注册的方法；Codex 保持账号认证，API-only 提供方和浏览器会话保持独立。可信 Host 从 localhost /api/tags 枚举 Ollama 模型，并经 /api/show 获取上下文上限。按内存保守限制实际上下文、输入与输出预算，通过脱敏 Remote 提供数据。用户明确请求时才用 /api/pull 下载并显示进度；解除关联不会删除共享文件，永久删除必须单独确认。超出分配上下文的本地请求直接报错。公共仓库不保存私密目录或凭据；发布仍需 CI 通过。

## OpenAI 路由选择的后续修正

最初弹窗在 `openai` 条目下仅显示 API，尽管用户会自然预期还有 ChatGPT/Codex 账户认证。这里不是 OpenAI API 缺失 OAuth，而是两条独立路由：`openai` 使用 API，`openai-codex` 使用原生 Codex 账户会话。修正后的弹窗在两条路由可用时统一呈现 API 与 AUTH，用户选择后切换实际路由，不混用订阅凭据与 API 密钥。其他提供方的 OAuth 仍来自 pi-ai 实际注册的授权方法，绝不虚构登录方式。授权列表只接受 `llm-pi-ai/` 范围或原生 Codex 的精确键，避免其他连接器被误认为模型登录。认证列表加载失败时显式提示并允许重试。
