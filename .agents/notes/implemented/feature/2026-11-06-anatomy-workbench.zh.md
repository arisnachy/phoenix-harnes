# Agent Note：本地解剖研究工作台

Status: implemented

[English](2026-11-06-anatomy-workbench.md) | 中文

## 问题

PHOENIX 可以解释医学影像，但此前无法在本地从真实三维影像生成并检查体积表面。仅凭心电图、X 光片、病史或通用分割模型便声称重建了准确的患者个体解剖结构，会造成误导。

## 决定

在 `scripts/phoenix-anatomy-reconstruct.py` 提供明确标记为研究用途的 CT/MR 流水线：可通过 TotalSegmentator 分割体积影像，也可导入临床人员提供的 NIfTI 掩膜，输出 GLB 网格并记录来源与不确定性。模型权重使用独立私有缓存，关闭可选的上游使用统计，并且不把患者图像路径传入通用提示词。Windows 更新流程在独立用户目录安装可选依赖，失败不阻塞 PHOENIX。Node 本地查看器只通过回环地址、随机访问令牌和本地固定版本 Three.js 提供明确指定的研究文件。Kira 可使用不读取患者档案的解剖规划及环境状态工具。

## 备选方案

将逼真的通用心脏图像当作患者数字孪生会捏造解剖信息。上传 DICOM 到托管查看器会增加第三方数据暴露风险。把所有研究引擎直接打包进主程序会扩大更新体积和启动故障风险。不允许把未经审核的分割结果直接用于自动治疗建议。

## 后果

如果影像质量、模型权重和本地资源满足要求，工作台可以生成研究用途的网格，但不代表已完成诊断验证、医疗器械合规评估、正式病历签署或 OHIF/DICOM 切片联动。规划目录涵盖超出 TotalSegmentator 训练任务的器官系统，包括周围神经及小血管；这些结构需要专项验证模型或专家分割。SimVascular 与 openCARP 仍需独立验证运行平台，不能伪称已安装。

## 验证

Node 测试覆盖启动、安装状态、查看器访问控制及拒绝不实临床标记；规划测试涵盖西班牙语解剖术语、心电图不确定性和非体积影像。正式 Windows 安装、完整 DICOM 分割、模型精度及访问控制还需在支持的平台上执行 CI 和专家审阅影像，才能开展临床部署。
