# Windows local accelerator provisioning pilot

Status: experimental; calibration results are not yet consumed by the production inference manager.

The successful managed PowerShell update launches a detached, user-scoped provisioning worker for llama.cpp b10964. It inspects healthy PCI graphics adapters and stages compatible candidates under PHOENIX_HOME (default ~/.phoenix), verifies pinned SHA-256 digests, and requires compute-device enumeration. When an installed managed GGUF is selected in on-demand mode and no local inference process is observed, it compares the installed CPU runtime with compatible candidates using 256 prompt and 64 generation tokens, three repetitions, and requested 8/16/99 GPU layers. It checks free RAM before each benchmark and bounds each subprocess to two minutes. Without a CPU baseline, provisioning stops after the first usable candidate. The ranking rejects GPU measurements without positive layer-offload diagnostics, and retains CPU unless a measured GPU reduces estimated workload time by a factor of at least 1.10. Partial comparisons are marked incomplete. No system drivers are installed. Existing model files, Ollama, Orión and the active inference runtime are unchanged.

Set PHOENIX_LOCAL_ACCELERATOR_AUTOINSTALL=0 to disable provisioning. Status and installer.log are under local-models/accelerators/b10964; node scripts/phoenix-local-accelerators.mjs --status reads the last recorded result.

A process check does not guarantee exclusivity against a concurrent launch. A crashed worker may leave a lock requiring verified manual cleanup. Windows archive extraction, actual device use, benchmark diagnostics, memory safety, integration into the managed local model lifecycle and CPU fallback during inference remain release gates. Do not promote the draft until those checks pass.
