# Agent Note: Codex live model autodiscovery

Status: implemented

## Problem

`openai-codex` 路由可以通过本地 Codex 安装进行身份验证，其配置界面也可以查询 Codex `model/list`，但运行时目录在用户明确采用模型条目之前仍停留在已安装的 pi-ai 快照。因此，账户刚获得的新模型可能已经存在于 Codex 中，而 Phoenix 仍会把该模型 id 拒绝为 `UNKNOWN_MODEL`。

## Decision

Phoenix 将本地已认证 Codex 的 `model/list` 响应作为已配置 `openai-codex` 路由的仅运行时目录覆盖层。该覆盖层不会自行激活 Codex，也不会把自动生成的模型条目写入 `settings.yaml`；用户拥有的模型字段与模型覆盖项会叠加到发现结果之上，因此显式调优保持优先，同时新公布的模型 id 自动可用。

pi-ai 适配器会在模型选择器列出模型之前刷新 Codex 目录，并在精确 Codex 模型查询未命中当前快照时执行一次刷新后重试。插件还会在 Codex 路由存在或发生变化时异步预热目录。刷新失败或返回空列表时会保留此前可用的目录，并且在下一次成功刷新清除失败状态之前最多记录一次警告。

每次成功的目录变化都会替换内存目录的身份。下一次适配器操作会根据该覆盖层解析新的不可变配置代，而已经捕获某一代配置的调用继续使用启动时的模型元数据和分发配置。

## Alternatives considered

**把每次发现结果持久化到 settings。** 未采用，因为账户可用性属于会变化的提供方元数据，而不是用户决策；持久化会产生无意义的 settings 差异，让过期条目看起来像是有意配置，并把提供方拥有的事实与用户拥有的调优混在一起。

**按固定计时器轮询 Codex。** 未采用，因为反复启动 app-server 会在 Phoenix 空闲时消耗主机资源，还会为了弥补缺少需求信号而引入一个随部署变化的时间间隔。选择器读取与未知模型未命中本身就是精确的新鲜度信号，而异步预热覆盖启动和 settings 激活场景。

**只信任 pi-ai 随包目录。** 未采用，因为 Codex 账户可用性可能在依赖快照发布之前就发生变化，而自动发现正是为了覆盖这段时间差。

## Consequences

只要本地已认证的 Codex 安装开始公布某个模型，Phoenix 就能使用它，而无需等待 Phoenix 发布版本或硬编码模型 id。手动的逐模型调优仍然具有最高优先级。新发布的模型不会激活一个尚未配置的 Codex 路由；实时发现中断时，系统会退化到最近已知或静态目录，而不是移除仍能工作的模型。该设计有意在相关活动发生时刷新，而不是在应用空闲时持续轮询。
