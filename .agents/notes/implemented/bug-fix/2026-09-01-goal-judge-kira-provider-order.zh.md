# Agent Note: Explicit goal judge routing and KIRA preferences

Status: implemented

[English](2026-09-01-goal-judge-kira-provider-order.md) | 中文

## Problem

完成评审器在启动时没有显式模型选择，而是继承执行模型，因此 Codex 任务不能可靠地使用要求的 Luna xhigh 评审器。目标驱动器还会在一次尝试被取消后暂停活动目标，模型选择器也没有持久化的提供方顺序或助手身份设置。

## Decision

`judgeGoalCompletion` 现在会在启动只读评审器前解析明确的子代理选项。`openai-codex` 父代理将评审器路由到 `gpt-5.6-luna` 并使用 `xhigh`；其他父代理保留其精确的提供方、模型和推理强度，只有未选择强度时才发现提供方公布的最高强度。目标提示词明确 `update_goal(action=complete)` 是激活评审器的入口，被取消的尝试会作为活动恢复事件继续。

本地用户资料命名空间现在拥有默认的 KIRA 名称、男性化/女性化/中性呈现以及可选的提供方顺序。身份通过独立提示词上下文请求自然对话，但不把助手误称为人类。模型设置会持久化相邻提供方移动，宿主会将相同顺序应用于建议模型分组，但不会隐藏路由。

## Alternatives considered

**继承父代理路由：**拒绝，因为评审器必须独立于执行模型，并且无法执行所要求的 Codex 到 Luna 评审。

**把提供方顺序当作路由允许列表：**拒绝，因为显示偏好不能使已注册提供方不可用。

**在尝试取消后暂停：**拒绝，因为尝试取消不是持久任务完成或阻塞的证据。

## Consequences

评审器不可用或路由能力失败时仍返回结构化 `blocked` 结果，因此任务保持活动状态并可进入下一次恢复轮次。提供方顺序写入需要正常可写的设置服务，并在宿主镜像刷新后可见。现有资料值会通过模式获得新增身份字段的默认值；清除身份会恢复 KIRA 和中性呈现。

## Testing

聚焦测试覆盖 Codex/Luna 路由、非 Codex 路由保持、提供方顺序排序与持久化、资料默认值与校验以及宿主排序工具。受影响的目标、资料、客户端设置和 API 网关包均完成类型检查。
