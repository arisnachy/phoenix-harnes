# Agent Note：MCP OAuth Host 确认响应

Status: implemented

[English](2026-10-12-connector-oauth-host-acknowledgement.md) | 中文

## 问题

浏览器将 `authorization.begin` 的等待时间限制为十二秒。此前 Host 创建待处理的授权尝试后，会在解析 RPC 响应之前立即调用提供方。某些 OAuth 流程在第一次异步暂停之前会执行同步工作，导致初始确认被延迟，即使授权尝试已经创建。浏览器的超时消息还固定提及 Notion，掩盖了 Slack 和 Meta 集成的真实错误来源。

## 决定

Host 同步记录授权密钥和方法，但将提供方的执行安排到下一个事件循环轮次。这样，初始 RPC 就能在不等待 OAuth 准备过程的情况下返回。如果用户在提供方启动前取消，Host 会将尝试标记为已取消并释放待处理的密钥，而不会运行提供方。

浏览器现在会正确标明发生超时的连接器，并将错误报告为缺少 Host 确认，而非上游 OAuth 失败。它不会虚称连接器已授权，也不会编造提供方授权网址。

## 考虑过的替代方案

**增加十二秒的 RPC 超时时限。** 未采用，因为延长等待会掩盖 Host 阻塞问题，且仍保留误导性的错误提示。

**同步启动提供方，再逐一优化连接器。** 未采用，因为任何独立的提供方都可能引入同类启动延迟；Host 的确认响应应当与提供方无关。

## 影响

本地 Host 的启动请求与提供方 OAuth 工作分离。初始确认之后，提供方仍可能在 OAuth 发现、客户端注册、重定向验证或用户同意阶段失败。尤其是，这项修改不会绕过 Slack 对已注册 OAuth 客户端的要求，不会将个人 WhatsApp 变为 Business Cloud API，也不会消除 Meta 的 OAuth 兼容性限制。只有 MCP 连接实际运行并发现工具后，才能认定连接器就绪。

## 验证

回归测试覆盖了在启动提供方之前确认请求、启动前取消、现有 OAuth 状态与提示交互，以及 Slack 和两个 Meta 连接器各自的超时文本。修改通过 GitHub 完成；编写环境中未执行真实 Windows Host、Slack 或 Meta OAuth 测试。在宣称连接可用前，还需通过 CI 和经过提供方授权的实际检查。
