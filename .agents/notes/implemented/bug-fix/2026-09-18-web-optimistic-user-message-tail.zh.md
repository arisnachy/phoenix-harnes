# Agent Note: 将乐观用户消息保持在文本记录尾部

Status: implemented

[English](2026-09-18-web-optimistic-user-message-tail.md) | 中文

## 问题

编辑器已经提供本地 pending-submit 投影，让按下 Enter 后无需等待 Host 接纳完成就能显示发送结果，但 ChatView 把这个投影渲染在持久聊天流之前。于是新发送的用户气泡会出现在已加载历史上方，并可能一直位于屏幕之外，直到 Host 发出持久化 `user/message`；随后乐观行消失，同一消息又在持久位置重新出现，看起来就像文本记录在延迟数秒后自行重新排序。交接逻辑还会把 Host／浏览器一秒时钟抖动窗口内的任何用户行当成刚发送的消息，因此一条无关的近期提示也可能压掉新的乐观气泡。

## 决策

普通待提交消息由聊天流所有者渲染在 transcript（文本记录）尾部：位于所有当前持久节点之后、当前运行轮次状态之前。该投影仍然只属于展示层：它不会进入会话日志、模型上下文、工具路由、记忆、检索或提供商请求。对应的持久化 `user/message` 到达后，乐观投影消失，由带稳定 key 的持久用户行占据同一阅读尾部，因此不会再发生从头部跳到尾部的视觉重排。

持久交接保留原有一秒时钟抖动宽限，但收紧向过去时间的匹配。时间戳等于或晚于浏览器接纳开始时间的用户行可视为 Host 回显；如果用户行更早但仍在宽限窗口内，只有其纯文本投影与待发送文本一致时才视为同一条消息。这样可避免紧邻的新发送之前那条无关提示隐藏新气泡，同时继续容忍小幅 Host／浏览器时钟偏差。

贴底跟随的流尾签名包含待提交接纳开始时间。因此已经钉在底部的读者会在 React 发布乐观行后立即看到它；主动离开底部的读者则继续按现有滚动 ledger 保有滚动所有权。

## 测试

`packages/client/ui-conversation/tests/chat-view.client.spec.tsx` 先放入一条处于抖动窗口内的旧用户消息和一条已完成助手消息，再发布新的待提交消息，并断言乐观气泡存在且位于旧回复之后。随后追加持久用户行，断言只剩一个副本并维持相同尾部顺序。该单一场景同时能让旧的头部插入逻辑和旧的无关消息时钟匹配逻辑失败。

组装后的 Web replay 车道继续作为持久 transcript 与流式行为的权威验证。本次变更不改变任何持久事件或模型可见输出；新增状态只存在于本地接纳的短暂区间，因此包级测试负责该瞬态交接，既有 Web replay 继续覆盖最终稳定文本记录。

## 曾考虑的替代方案

**等待 Host 持久行后再显示。** 否决，因为虽然消除了视觉重排，却会重新引入发送延迟回归：用户必须等到传输接纳结束才看到消息确认。

**继续把乐观行放在持久流之前，只滚动过去显示它。** 否决，因为滚动只能把错误的时间顺序变得可见；待发送消息应位于它所跟随的历史之后，而不是历史上方。

**把时钟抖动窗口内的所有用户行都视为匹配。** 否决，因为快速连续发送时，无关的上一条用户消息可能落入窗口，从而错误地把新的提交判为已经持久化。

**把接纳或模型工作切换到更低质量的快速路径。** 否决，因为缺陷来自展示顺序，而不是模型执行。回复质量、检索、记忆、工具、提供商路由和流式输出全部保持不变。

## 后果

发送操作无需等待 Host 持久化就能在正确阅读位置获得确认，乐观到持久的交接也不再视觉上重排会话。该修复不增加模型 token 工作，也不增加子代理或检索路径。唯一新增的渲染输入只是 InputState 已经持有的待提交时间戳；交接完成后，持久历史仍然是唯一事实来源。
