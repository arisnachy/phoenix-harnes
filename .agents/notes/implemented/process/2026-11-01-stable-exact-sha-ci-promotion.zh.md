# Agent Note: 按准确 SHA 验证 CI 后以非强制方式发布 stable

Status: implemented

[English](2026-11-01-stable-exact-sha-ci-promotion.md) | 中文

## 问题

连续的小型 PR 提交会反复触发昂贵的 CI。仅通过 Windows main guard 不能证明来源 PR 的全部检查都通过；旧的 stable 发布流程虽然检查了提交祖先关系，仍使用带强制能力的推送。DeepSeek 工作流显示绿色但真实 E2E 任务被跳过时，也不能视为真实 API 测试通过。

## 决定

自动发布 stable 必须验证当前 main 的准确 SHA、main 推送的 guard 成功，并独立确认来源于已合并 PR，且该 PR 的准确 HEAD 已成功完成所有适用的工作流。真实 DeepSeek E2E 任务必须单独成功，不能只依赖配置检查的绿色结果。API 证据缺失、等待、失败或截断时一律拒绝发布。

stable 仅在祖先检查通过后使用普通的非强制 Git 推送推进。随后重新获取 main 和 stable，并核对它们是否等于同一个已验证 SHA。没有相应已验证 PR 的直接推送无法发布到 stable。完整 CI 保持不变；贡献者应先汇总修复并重用准确 SHA 的已有结果，避免每次仅改几行就反复触发 CI。

## 备选方案

- **祖先检查后使用 force-with-lease。** 即使检查通过，具有强制能力的引用更新也不符合非强制发布要求。
- **仅依赖 main guard。** 无法发现来源 PR 中不相关的静态检查、覆盖率、快照和消费者测试失败。
- **只看 DeepSeek 工作流状态。** 配置检查可能通过，但真实 E2E 任务被跳过。
- **缺少远端证据时继续发布。** 这会将临时 API 或凭证故障变成未经授权的发布。

## 后果

通过验证的合并在 main 的准确 SHA guard 结束后自动发布到 stable，无需手动操作；不安全的合并即使出现在 main 也不会传播到 stable。仓库仍需管理级分支规则以阻止直接推送 main；该严格发布检查不能替代分支保护。真实 E2E 凭证和失败的测试仍须先修复。

## 测试

Node 回归套件覆盖合法 CI 证据、错误 SHA、缺失或失败的工作流、等待中的任务、被跳过的真实 E2E 和条件性不适用的工作流。常规静态 CI 执行这些测试，stable 发布流程也会先执行，再查询实时 GitHub 证据。
