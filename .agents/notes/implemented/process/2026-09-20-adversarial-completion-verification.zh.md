# Agent Note：对抗式完成验证

Status: implemented

[English](2026-09-20-adversarial-completion-verification.md) | 中文

## 问题

PHOENIX 可能让自己编写的测试套件全部通过，但仍然交付测试从未覆盖的用户可见故障。一次外部对比明确暴露了这种模式：生成的计算器通过了 44 个测试，但单参数 `max`/`min`、零的负指数以及深度嵌套或连续一元运算仍会泄露原始运行时异常或 traceback。测试套件只证明了选中的样例，而没有证明重要失败类别不存在。

## 决策

固定 harness 身份现在要求每个普通 PHOENIX 智能体都以对抗式、真实入口为基础提供完成证据。测试通过只是证据，不是完成证明。在宣布重要工作完成前，智能体必须运行真实用户入口或生产入口，并主动覆盖最有价值且适用的失败类别：数量 0/1/多、边界和极值、畸形输入、深层或超大输入、依赖失败、超时/取消以及生命周期或资源清理。

当输入空间很大时，如果属性测试、fuzz 或 metamorphic 检查比少量示例提供更好的覆盖，应优先采用。真实观察到的失败优先于绿色测试套件。用户可控输入必须得到有效结果或领域分类错误；实现异常、原始 traceback、部分写入和静默数据损坏不能跨越用户边界。内部诊断仍保留完整细节。

每个被发现的失败在完成前都需要三件事：修复根因、加入本应能够捕获该问题的回归测试，并重新运行受影响的真实入口。重要的多步骤交付在可用时使用持久目标及其独立完成裁判；否则使用新的独立验证器，避免作者成为自己测试的唯一裁判。

PHOENIX 还在 base bundle 中挂载 `@phoenix-ai/dsh-quality-policy`，作为机械化的低延迟证据新鲜度 guard。它为每个 agent 维护 O(1) 的任务账本：成功修改会推进 evidence generation；之后观察到的验证只让当前 generation 变为新鲜；后续修改会立即使它失效。第一次从“新鲜”变为“脏”时，只通过本来就在继续的工具结果 `additionalContexts` 附加一条短 notice，因此正常合规路径不会增加模型轮次。如果轮次仍试图在“脏”状态下结束，`agent/turn-stopping` 默认最多 steer 一次有界纠正。领域提示要求 code、web、config 使用自动化证据，而 docs、data、generic 可以使用最终检查。提醒明确要求先用确定性检查，再考虑模型评审；独立检查尽量并行；输入未变化时复用新鲜证据；优先真实消费入口；只有预期质量收益足以补偿延迟或成本时才增加验证。热路径刻意使用 generation 新鲜度而不是内容 hash，从而不增加额外文件系统 I/O；跨任务持久失败索引仍属于 learning 子系统。

仓库中的 AGENTS 规则与运行时约束保持一致，使修改 PHOENIX 自身的编码智能体遵循同一标准。system-prompt 测试固定关键措辞，因此削弱该约束必须成为显式、可审查的变更。

## 考虑过的替代方案

**只依赖 prompt 指导。** 这样没有额外 runtime 机制，但基准测试已经证明，自写测试仍可能留下过期或不完整证据而没有被阻止。

**每项任务后都调用独立模型裁判。** 这会加强复核，但即使确定性证据已经新鲜，也会增加延迟和 token 成本。当前方案只把模型裁判用于重要工作，正常路径使用本地 O(1) 新鲜度账本。

**每次工具调用后都对修改产物做内容 hash。** 内容寻址更精确，但无条件文件读取会增加 I/O，并把 guard 绑定到存储语义。Generation 新鲜度更保守、便宜且 provider-neutral；未来当修改工具可以零额外读取地暴露权威 hash 时，可以再替换。

## 后果

- 当真实 CLI、UI、API、可执行文件或其他生产入口仍然失败时，绿色单元测试不能再作为完成依据。
- 计算器对比中泄露的 `TypeError`、`ZeroDivisionError` 和 `RecursionError` 模式被提升为通用对抗失败类别，而不是一次性补丁。
- 验证成本保持成比例：智能体选择最有价值且适用的失败类别，而不是对每个微小改动进行无界 fuzz。
- 外部评估器发现的失败会反馈到 PHOENIX，转化为回归覆盖和更强的可复用完成策略。
