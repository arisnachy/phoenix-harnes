# Organization Forge 设计

[English](2026-08-31-organization-forge-design.md) | 中文

## 目标

Organization Forge 是一个可选的目标域能力，用于创建企业、系统或组织的请求。它协调研究、经过审计的复用、设计、构建、验证和交付，同时保留现有目标引擎、工具、沙箱、权限和会话日志的独立职责。

Forge 必须保留用户的准确目标、交付物、验收标准、质量要求和验证证据。失败的尝试、工具、计划或可复用来源都不能关闭 Forge 构建。

## 现有基础

`OrganizationForgeLedger` 已经通过 `organization-forge/change` 事件将 Forge 快照持久化到所属会话。实现将扩展该 ledger 及现有的 `organization_forge` 面向模型工具，而不是增加第二个目标数据库或并行执行循环。

## 生命周期

持久化生命周期为 `researching → auditing → designing → building → verifying → ready`。`blocked` 表示当前无法解决的外部依赖，并且可以恢复；它不是成功的终止状态。

`start` 创建一个目标锁定的 Forge 快照。除非用户提供更严格的列表，否则默认要求功能、测试、安全、可观察性、可维护性和文档标准。快照还记录当前目标引用（如果存在），因此 Forge 的完成不能脱离发起它的任务。

`research` 通过现有网络和连接器职责记录可比产品、仓库、工具、架构模式和公开证据。研究条目只包含公开定位符、发现和相关性；凭据、客户私密信息和敏感原始内容都被排除。

`audit` 为每个复用来源记录复用前和修改后的检查。审计涵盖许可证兼容性、依赖来源、秘密扫描、漏洞、可疑行为以及每个结果对应的证据或发现。缺少两次通过审计的来源时，Forge 不能进入设计或构建阶段。

`design` 记录可复现的蓝图：组件、接口、基础设施、自动化、代理角色、工作流、指标、成本控制、性能目标以及适用时的收入或运营假设。确定性工作使用确定性自动化；模型只用于研究、设计判断和需要语义推理的任务。

`build` 和 `deliverable` 引用通过现有 Phoenix 工具和沙箱提供者产生的真实工件、执行、测试、部署和文档。交付物不会因为存在计划或进度消息而被验证；它必须具有来自所属执行职责的证据引用。

`verify` 在修改后重新验证复用资产，并记录功能、安全、可观察性、可维护性、文档、回归和质量证据。每次再次部署或交付前都必须重新验证。

`judge` 使用配置的独立只读评审器，结合原始目标、当前 Forge 版本、交付物、审计和证据进行评审。只有在所有必需标准已验证且每个复用来源两次审计通过时，`pass` 才能进入 `ready`。`needs_changes` 保持构建活动状态，并将所需修改保存为下一批工作。`blocked` 保存准确缺失的外部依赖，并在依赖可用时恢复。

## Phoenix 团队职责

Forge 暴露三种职责，但不创建永久团队名单。Phoenix IT 负责确定性构建、集成、测试、修复和运行诊断。Phoenix Security 负责权限审查、来源审计、秘密处理、威胁检查和运行时保护。Phoenix R&D 负责比较研究、实验、成本和性能方案以及可复用模式提取。

职责工作以当前证据和活动分配表示在 Forge 快照中。完成的分配会离开活动视图，但仍保留在持久事件历史中，因此界面只显示活动工作而不丢失审计记录。

## Atlas 与复用规则

只有在修改后的审计通过，并且条目已清理为公开、通用组件元数据后，Forge 才能发布可复用 Atlas 条目。Atlas 条目不包含客户名称、私密数据、凭据、令牌、私有原始文档或部署特定标识。每个 Atlas 或 GitHub 资产在再次复用前，都必须根据记录的来源和当前策略重新验证。

## 交付与管理

`ready` 是唯一的 Forge 交付状态。随后，面向模型的结果必须准确询问：“¿Quieres que Phoenix gestione también este negocio/sistema?” 用户选择 `Entregar`、`Gestión asistida` 或 `Gestión autónoma`。管理模式不会隐式启用，自主管理仍受现有权限代理和明确用户授权限制。

## 失败与恢复

Forge 将失败记录为尝试、审计、交付物或评审证据，并保持当前构建活动。可恢复失败会创建新策略或修复项目；重复相同失败时必须使用不同的策略标识。外部阻塞会以标准化依赖名称、原因、最后尝试时间和恢复条件进入 `blocked`。会话检查点足以在进程重启后恢复。

## 安全与边界

Forge 不会仅因为快照表示某个动作已计划，就授予权限、执行工件、修改工作区、发布到 GitHub 或控制业务。这些效果必须经过现有工具、沙箱、审批、连接器和部署职责。外部源代码在两次审计通过前都被视为不可信，模型声明不能将审计失败转换为 `ready`。

## 验收标准

- 直接的组织、企业或系统请求会创建一个带有锁定目标和必需标准的持久 Forge 记录。
- 在复用来源进入设计或构建前，必须记录研究证据。
- 每个复用来源在就绪前都必须通过复用前和修改后审计。
- 必须提供真实交付物和证据；进度文字、无关的通过测试或计划不能满足标准。
- 独立评审器将原始目标与当前交付物进行比较，并拒绝缺失、部分完成、不安全、未测试或未记录的工作。
- 评审拒绝会保持 Forge 活动，并暴露所需修改以进行下一次修复循环。
- Atlas 发布必须无秘密且可复用；私密或客户特定数据会被拒绝。
- Phoenix IT、Phoenix Security 和 Phoenix R&D 保持职责分离，不生成重复的永久团队名单。
- 最终管理问题和三个选项只会在质量检查通过后出现。
- 会话重放可以恢复当前 Forge 版本及其证据，无需第二个持久化存储。

## 延后范围

Forge 不替换目标继续驱动器，不实现通用企业生成器，不保证盈利，也不会在没有用户选择模式和现有权限的情况下启用自主生产管理。具体提供者部署、计费、受监管领域审查和真实外部凭据仍属于环境特定的验证工作。
