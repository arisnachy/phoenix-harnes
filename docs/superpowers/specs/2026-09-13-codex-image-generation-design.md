# Codex-Backed Image Generation Design

## Goal

Give PHOENIX a first-class `generate_image` capability that a selected agent can call from an ordinary conversation while reusing the official Codex runtime and its built-in image-generation tool. Generated raster bytes must become durable PHOENIX attachments and user-visible outputs rather than opaque text paths.

## Scope

This design covers text-to-image generation only. Image editing, masks, multi-image variation batches, video generation, and direct OpenAI Images API routing are intentionally outside this first implementation. The existing KIRA Teams visual redesign is a separate bounded UI change and does not depend on this subsystem.

## Current constraints

- PHOENIX already has a provider-neutral LLM seam, but its production adapters currently declare text-only output. The LLM content vocabulary nevertheless already permits durable assistant-side `image` blocks.
- PHOENIX already has `ctx.attachments`, including validated `saveImage`, `saveImages`, `readImage`, and image limits. Generated bytes must use this service rather than inventing another binary store.
- The Web client already knows how to render durable message images through the attachment presentation plugin and lightbox.
- The existing `@phoenix-ai/dsh-subagent-codex` package starts the official package-local Codex app-server with native Codex configuration and authentication. It currently returns final text only to its parent.
- Codex image generation is a Codex skill backed by the host's built-in image-generation tool. The bridge therefore must delegate to Codex rather than pretending the ordinary PHOENIX LLM adapter itself can produce an image.

## Chosen architecture

### 1. Model-facing consumer: `generate_image`

Add a focused model-facing tool package under the subagent capability family. The tool has one required field:

```ts
interface GenerateImageInput {
  prompt: string
}
```

The tool name is `generate_image`. Its description tells the parent model that it creates one raster image and returns a durable PHOENIX image plus a workspace file location. The tool does not expose Codex thread ids, provider internals, API keys, output directories, or manifest protocol.

The tool consumes the existing `ctx.subagents`, `ctx.attachments`, and the current initiating Agent/Session. It does not call OpenAI HTTP APIs itself.

### 2. Codex execution boundary

The tool starts the configured `codex` subagent provider in the current Session workspace. The delegated task is fixed around the user's prompt and instructs Codex to:

1. use its built-in image-generation capability, not a shell/API fallback;
2. generate exactly one final raster image;
3. write the selected image into a tool-owned output directory under the current workspace;
4. write a small JSON manifest beside it containing only the relative image filename and media type;
5. return only a short completion acknowledgement.

The output directory is minted by PHOENIX for each call (for example `.phoenix/generated-images/<call-id>/`). Codex is never allowed to choose a path outside this directory for the committed result.

### 3. Validation and commit point

After Codex settles successfully, PHOENIX reads the manifest and image from the fixed directory. Before publishing anything it validates:

- manifest JSON has exactly the expected fields;
- the resolved image path remains inside the minted output directory;
- the file is a regular file;
- the declared media type is one accepted by `ctx.attachments.imageLimits`;
- bytes decode through the existing attachment service and satisfy its size/dimension policy.

Only after `ctx.attachments.saveImage(...)` succeeds does the tool return success. The durable attachment reference is therefore the publication boundary. A Codex success without a valid image is a tool failure, not a partial success.

### 4. Tool result shape

The successful tool result contains typed content:

```ts
[
  {
    type: 'image',
    attachment: savedRef,
  },
  {
    type: 'text',
    text: 'Generated image saved to <relative-workspace-path>.',
  },
]
```

This uses the existing LLM `ImageBlock`, so later model turns can reason over the same durable reference when the selected route supports image input. Text-only routes receive the existing deterministic image placeholder policy.

The tool's presentation metadata also marks the workspace image path as a produced file so PHOENIX's existing deliverables behavior can surface it independently of whether the final assistant prose mentions it.

### 5. User-visible rendering

No second image store or bespoke base64 protocol is introduced. The conversation/render layer consumes the durable image reference through the existing attachment loader and image components. The generated image appears inline with the tool/assistant flow and can open in the existing image lightbox. A generated file path remains available as a normal PHOENIX deliverable.

### 6. Composition

The interactive Web profile must mount:

- the official `@phoenix-ai/dsh-subagent-codex` provider;
- the new Codex image-generation tool consumer;
- the already-mounted attachment service.

The core/base profile should not silently make every headless installation pay the Codex native payload cost. The image-generation rows belong to the Web app profile layer. If another profile wants image generation, it can opt into the same rows explicitly.

The tool is exposed only when the Codex provider and attachment service are both resolvable. Missing native Codex payload, unauthenticated Codex, or a Codex build without built-in image generation fails with a clear `IMAGE_GENERATION_UNAVAILABLE`-class diagnostic; PHOENIX does not request an API key as an automatic fallback.

## Failure and safety behavior

- Cancellation propagates to the Codex subagent and prevents attachment publication when it wins before commit.
- Codex text claiming success is never trusted; the fixed manifest and image bytes are authoritative.
- Path traversal, symlinks escaping the minted output directory, unknown media types, malformed manifests, empty files, and attachment-policy violations fail closed.
- Temporary call directories may be retained only when needed for the workspace deliverable. Failed-call temporary data is removed best-effort after the failure is classified.
- No raw Codex stderr, authentication token, provider payload, or hidden prompt is copied into the model-facing tool result.
- The generated image is not considered complete until the attachment store has validated and committed it.

## Testing

### Tool unit/contract tests

Use a fake subagent provider and real in-memory/test attachment seam to prove:

- the tool delegates the exact user prompt inside the fixed image-generation instruction;
- one valid generated PNG/JPEG/WebP is committed and returned as an `image` content block;
- a valid image location is reported as a produced file;
- malformed manifest, missing file, path escape, unsupported media type, failed Codex run, and cancellation all return safe failures without publishing an attachment.

### Real composition test

Boot the Web profile through the Loader with the image-generation rows enabled, substitute only the nondeterministic Codex process boundary, call `generate_image`, and observe the durable image reference and user-visible result. This satisfies the repository rule that product-visible plugins prove real composition.

### Codex compatibility test

Keep a small protocol/fixture test that asserts the delegated prompt requires the built-in image-generation path and rejects a shell/API fallback. Live credentialed image generation is not a merge gate because it is account- and quota-dependent; it is an optional smoke test.

## Acceptance criteria

1. A PHOENIX agent can invoke `generate_image({ prompt })` from a normal Web conversation.
2. The call runs through the official Codex subagent using native Codex authentication/configuration.
3. Success requires one validated image committed through `ctx.attachments`.
4. The conversation displays the generated image using existing PHOENIX image presentation and exposes the workspace result as a deliverable.
5. Text-only model routes degrade through the existing image-placeholder policy rather than breaking history replay.
6. Failures are bounded, safe, and do not publish partial attachment state.
7. The Web profile includes the capability; unrelated headless/base profiles do not gain the Codex native payload by default.
8. Tests cover success, unavailability, malformed output, path safety, cancellation, and real Loader composition.

## Implemented runtime composition

The Web profile mounts the official Codex subagent provider, and the standard interactive agent preset mounts the Codex-backed `image_generation` tool. The new package is part of the workspace lockfile and host TypeScript project graph; base/headless profiles remain unchanged. This wiring is intentionally explicit so a missing Codex provider fails closed instead of silently falling back to an external image API.

## Deferred work

A future design may add image editing/reference inputs, provider-neutral non-Codex image generators, multi-image batches, and richer generation controls. Those features must reuse the durable attachment seam and must not weaken the commit-point or path-safety rules above.
