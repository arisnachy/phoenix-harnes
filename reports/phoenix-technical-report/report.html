PHOENIX

Uso, arquitectura y controles operativos de un harness de agentes de IA local-first y agnóstico de proveedor.

Tesis. PHOENIX convierte un runtime extensible en una superficie operable y auditable: compone capacidades como plugins, conserva la continuidad de sesión localmente y mantiene separadas las credenciales, los proveedores y las políticas de ejecución.

01 · Uso real

Una sesión, varias capacidades coordinadas

PHOENIX coloca la configuración y la seguridad cerca del usuario, sin ocultar los límites de cada proveedor.

01

Elegir proveedor

OpenRouter se configura desde Settings → Models; ChatGPT/Codex usa su plano nativo de cuenta.

02

Componer sesión

Un perfil apila bundles y parches para decidir qué agentes, herramientas y políticas entran al runtime.

03

Ejecutar y conservar

La sesión registra eventos durables para que el historial local pueda proyectarse, reanudarse y auditarse.

Flujo de uso

Separación de identidades

La autenticación de API de OpenAI no se mezcla con la suscripción de ChatGPT. El puente nativo de Codex gestiona el inicio de sesión y la renovación OAuth; PHOENIX no pide la contraseña de ChatGPT ni persiste esos tokens.

Local-first con proveedor intercambiable

El proveedor, endpoint, catálogo y modelo activo se administran desde la UI. La continuidad de sesión permanece local por defecto y no se anuncia almacenamiento cloud sin una restauración comprobable.

“Model-visible means logged”: lo que llega a una petición de modelo debe poder reconstruirse desde el registro de sesión.
Fuentes: `README.md` (Configure OpenRouter; Connect ChatGPT / Codex), `docs/architecture.md` (Session log; Profiles and bundles).

Seams de capacidad

Definición · proveedor · consumidor

Una capacidad completa declara su interfaz, implementa el proveedor y expone un consumidor, con frecuencia una herramienta orientada al modelo.

Eventos como extensión

Los eventos de sesión conservan hechos; los eventos de agente y de capacidad permiten observar o interceptar trabajo vivo sin importar el loop.

HARDNESS

Indexa capacidades y enruta modalidades; no reemplaza los registros de herramientas o skills ni se convierte en autoridad de ejecución.

03 · Confianza técnica

Controles explícitos, límites visibles

La confianza se describe con la protección disponible y con el límite que todavía aplica.

Principio operativo

Una capacidad no se considera disponible solo por aparecer en un índice: las rutas `have` y `route` requieren evidencia de verificación actual.

Qué no se promete

No hay respaldo cloud anunciado hasta que existan recibos remotos y una prueba de restauración para la misma revisión.

Fuentes: `docs/phoenix-windows.md` (Native safety boundary; Continuity), `SECURITY.md`, `docs/architecture.md` (HARDNESS).

04 · Operación y estado

De checkout a runtime verificable

La operación combina instalación reproducible, checks de proyecto y una postura de desarrollo activo.

Instalación Windows

Bootstrap dedicado

El instalador crea un checkout gestionado, instala dependencias, construye la revisión exacta y crea el acceso directo PHOENIX HARDNESS.

irm .../install-phoenix.ps1 | iex

IDE

VS Code y Cursor

El paquete VSIX inicia el runtime local y abre la Web UI sin leer credenciales de modelos.

pnpm run package:vscode

Checks relevantes
  • TypeScript: pnpm run typecheck
  • Build completo: pnpm run build
  • Documentación: pnpm run doc-sync
  • Website: pnpm run website:build
  • Pruebas unitarias: pnpm run test
  • Higiene: pnpm run hygiene
  • Gate Windows: pnpm run check:ci:windows-complete
  • Soporte: Issues y Discussions del repositorio.
